1. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/ui/player/PlayerActivity.kt:240 and :242 (consumed at Gestures.kt:98 and :118). `_volumeFlow.asStateFlow()` and `_triggerVolumeIndicatorFlow.asStateFlow()` are called inside composition, so every root recomposition passes new flow instances, restarting `collectAsState` and `LaunchedEffect(triggerVolumeIndicatorFlow)`, which replays the last timestamp.
   - Scenario: after one hardware volume press, the volume indicator pops up for 1 s on every controls toggle, auto-hide, play/pause and PiP exit, and continuously during a pinch (see 2).
   - Fix: expose both as `val ... = _x.asStateFlow()` fields on the activity and pass those.

2. PlayerActivity.kt:209 (also :208 with :248). `zoomState.collectAsState()` is read at the `setContent` root, and `setVideoZoom` writes `_zoomState` on every pinch move (PlayerEngine.kt:721).
   - Scenario: every pinch pointer event recomposes the root and `GestureLayer`, re-running the `audioManager.getStreamMaxVolume` call (:241) and the `window.attributes` read (:234) on main, and triggering item 1.
   - Fix: pass the `StateFlow` (or a `() -> Double`) down and collect it only in `ResetZoomButton`; compute `maxVolume` once in `onCreate`.

3. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/ui/player/Gestures.kt:132, with :85, :94, :99. The `pointerInput(enabled, isLocked)` detector keeps whatever it captured when its coroutine started: the `durationMs` value and the state instances from `remember(zoom)`, `remember(initialBrightness)` and `remember(currentVolume)`. Those `remember`s create a new state object whenever their key changes, so the gesture writes one object while the UI reads another.
   - Zoom: zoom in, tap "Reset Zoom" (:448 resets the newest instance), pinch again; `baseZoom` (:173) reads the old instance and the picture snaps back to the pre-reset zoom. Same after `load()` resets zoom.
   - Brightness: after a brightness swipe and any root recomposition (tap, auto-hide), the next swipe changes window brightness but `BrightnessIndicator` (:414) reads the new instance and stays frozen.
   - Volume: touch the screen once, change volume with hardware keys, then swipe on the right; the volume jumps to the stale `localVolumeFraction` (:285).
   - Duration: after `onNewIntent` opens another file, or if the first touch came before duration was known, swipe seek clamps to the old `durationMs` (:238, :263); with a captured 0 the commit seeks to the start. Exactly when the handler is captured (first touch vs first composition) is unverified.
   - Fix: un-key those `remember`s and sync them with `LaunchedEffect`/`SideEffect`; read parameters through `rememberUpdatedState`.

4. /home/rava/vibeplayer/player/src/main/java/com/vibeplayer/player/PlayerEngine.kt:835-838, with DebugOverlay.kt:39-41 and PlayerEngine.kt:212, :231, :550. `release()` shuts down `commandExecutor`, but most engine methods call `commandExecutor.execute` without a shutdown check (only `detachSurface` has one, :329).
   - Scenario: finishing the player with the debug overlay open. `onCleared` runs `release()` before the composition is disposed, then `onDispose { setStatsEnabled(false) }` throws `RejectedExecutionException` on main. The same can happen on the mpv event thread (`END_FILE` -> `logStats`, `aid`/`sid` -> `updateTracks`) between `shutdown()` and the destroy task clearing the callback.
   - Fix: route all posts through one helper that no-ops after shutdown, or catch `RejectedExecutionException`.

5. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/ui/player/PlayerViewModel.kt:375 (called from PlayerActivity.kt:583 `onStop` and PlayerViewModel.kt:393 `onCleared`). `runBlocking(Dispatchers.IO)` on main waits for `currentPositionMs()`, a synchronous mpv `getProperty` on the command thread, plus a Room read and write. This breaks the "no blocking mpv call on main" rule; only `surfaceDestroyed` is exempt.
   - Scenario: leaving the player while `loadfile`, `reconfigure` or `updateTracks` rescans are queued stalls main for 500 ms and the position is not saved. Whether the 500 ms timeout really bounds the wait once the call is queued on the command thread is unverified.
   - Fix: save from the already-known `position`/`state` values in a non-cancellable IO coroutine on an application scope.

6. Gestures.kt:325 vs :359-362. Every single tap waits 200 ms before `onSingleTap`; the job then zeroes `lastTapTime`, so the declared 250 ms double-tap window is effectively 200 ms.
   - Scenario: controls always appear 200 ms after finger-up; a second tap 200 to 250 ms after the first toggles the controls twice instead of skipping.
   - Fix: one shared constant; or toggle controls immediately and undo it when a double tap is detected.

7. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/ui/player/PlayerControls.kt:374-378, read at :90 and :355-356. `seekProgress`, `userSeeking` and `lastInteraction` are written on every slider drag event and read in the `PlayerControls` body and the `AnimatedVisibility` content scope.
   - Scenario: scrubbing recomposes the whole controls overlay per drag event and cancels/relaunches the auto-hide `LaunchedEffect` each time.
   - Fix: pass the scrub position to `CurrentPositionLabel` as a lambda or State; keep `lastInteraction` out of composition (e.g. a conflated channel with `collectLatest`).

8. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/ui/player/SpeedSheet.kt:82-84 -> PlayerActivity.kt:285 -> PlayerViewModel.kt:260-276. The speed slider calls `viewModel.setSpeed` on every move, and each call does a Room `getByKey` + `upsert`.
   - Scenario: one slider drag produces dozens of DB writes, each invalidating the browser's history flow and each triggering a PiP params rebuild (item 12).
   - Fix: apply speed to the engine on change, persist in `onValueChangeFinished`.

9. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/ui/Nav.kt:57, :58, :109, :159. Flows are created inside composition without `remember` (`observeHistory()`, `observeAllVideos()`, `observeFolders()`, `observeVideosInBucket()`), so each recomposition of that scope resubscribes.
   - Scenario: every history or MediaStore change causes a second round of ContentObserver re-registration, a full MediaStore query and a Room re-query. Collection also keeps running while MainActivity is stopped under the player (10 s saves).
   - Fix: `remember` the flows or move them to a ViewModel with `stateIn`; use `collectAsStateWithLifecycle` (dependency already present).

10. Nav.kt:74-101. `File.exists()`, `length()`, `lastModified()` and a history x videos `find` with `normalizePath` run inside `remember` during composition on main.
    - Scenario: runs on every history emission (every 10 s while a PiP video plays over the browser); slow with deleted files or large libraries. The `displayName == fileName` fallback (:80) also matches a same-named file in a different folder.
    - Fix: compute in a `flow.combine(...).flowOn(Dispatchers.IO)`; match on path only.

11. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/data/media/MediaRepository.kt:147-219. Each `onChange` launches its own unconflated full-table query (`getVideosInBucket` also loads everything and filters, :142), and results are sent in completion order.
    - Scenario: a scan or download burst fires many `onChange` calls; the folders screen runs two full queries per change and an older result can land last, leaving a stale list.
    - Fix: send `Unit` into a conflated channel, `debounce` + `mapLatest`, share one query via `shareIn`, use a `BUCKET_ID` selection.

12. PlayerActivity.kt:186-190 (builder in PipHelper.kt:65-137). PiP params are rebuilt on every `PlayerState` emission: 3 `PendingIntent.getBroadcast`, 3 `Icon`/`RemoteAction`, and `setPictureInPictureParams`, all on main. It is not per position tick, because position is a separate flow.
    - Scenario: the burst of 10+ state changes at file load, each speed-slider step, buffering flips and track updates each cost several binder calls.
    - Fix: `state.map { (videoWidth, videoHeight, paused, durationMs > 0) }.distinctUntilChanged()` before collecting.

13. PlayerActivity.kt:343-344 (bodies at :355, :372), :417-418, and PlayerViewModel.kt:64-65. `contentResolver.query`, `openFileDescriptor` and `File.exists/canRead/length` run on main in `onCreate`/`onNewIntent`/`openVideo`.
    - Scenario: opening a `content://` video from a slow provider blocks the first frame of the activity.
    - Related defect: for content URIs the resume key becomes `fdclose://<fd number>` and the folder key `fdclose:` (PlayerViewModel.kt:72, :76), so positions and track choices are stored under a reused fd number.
    - Fix: resolve inside the `openVideo` coroutine on IO; key on the content URI plus size.

14. PlayerControls.kt:78-83 and PlayerEngine.kt:291, :309, with PlayerActivity.kt:230. `time-pos` observation is not stopped when `PlayerControls` leaves composition, and `setControlsVisible(true)` re-observes without checking.
    - Scenario: entering PiP from the controls button leaves `time-pos` firing for the whole PiP session; on return it is observed twice, so each tick arrives twice until the next hide. At startup it is also observed twice (`initHandle` + first `LaunchedEffect`), and `reconfigure` re-observes even when controls are hidden.
    - Fix: `DisposableEffect { onDispose { setControlsVisible(false) } }` and an idempotent observed flag in the engine.

15. Nav.kt:174-179 with MediaRepository.kt:25-39. `scanFolder` (`listFiles` + per-file `isFile`) is a non-suspend function launched from `rememberCoroutineScope`, so it runs on main.
    - Scenario: tapping refresh on a large folder janks the list.
    - Fix: make it `suspend` with `withContext(Dispatchers.IO)`.

16. PlayerViewModel.kt:70-75. `openVideo` sets `currentKey` immediately but loads asynchronously, and earlier jobs are not cancelled.
    - Scenario: two quick intents can finish out of order so the earlier file loads last; a periodic save in the gap writes the old file's position under the new key, which the new file may then resume from (narrow window, unverified in practice).
    - Fix: keep a `loadJob`, cancel the previous one, set `currentKey` just before `load`.

17. /home/rava/vibeplayer/app/src/main/java/com/vibeplayer/data/thumbs/ThumbnailCache.kt:93-170. No in-flight dedupe per key, writes go straight to the final file name, and results of cancelled requests are discarded.
    - Scenario: the continue-watching card, folder row and video row for the same file each extract and write the same `.webp`; a reader can see a partial file, fail to decode and delete it (:137). During a fling, in-flight extractions finish but are thrown away and repeated on scroll-back.
    - Fix: a `Map<key, Deferred>` in a cache-owned scope; write to a temp file and rename.

18. PlayerViewModel.kt:41-46. The periodic save runs every 10 s regardless of pause or background state.
    - Scenario: a paused or stopped player keeps doing a command-thread hop plus a Room upsert every 10 s, each invalidating the browser's history flow.
    - Fix: run the loop only while `!state.paused` (`collectLatest` on paused).
